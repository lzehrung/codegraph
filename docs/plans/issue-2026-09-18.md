# Codegraph: `refs` returns no cross-file references for TypeScript `enum` declarations

**Version:** `@lzehrung/codegraph` 2.3.27
**Repo:** `org-name-core` — npm workspaces monorepo, ~15,000 indexed files, TypeScript
**Severity:** answers are wrong, not merely incomplete, and are reported as high confidence

## Summary

`codegraph refs` on a `export enum` declaration returns only the references inside the
declaring file. Every cross-file reference is missing. A function in the same repository,
imported the same way, resolves correctly.

The result is labelled `resolution: "exact", confidence: "high"`, so nothing signals that the
answer is partial. A caller who trusts it concludes the enum has no external consumers.

## Reproduction

Three queries against the same index, same command shape:

```bash
codegraph refs "packages/shared/src/statements/models/statement-config.model.ts::ColType" --json
codegraph refs "packages/shared/src/statements/models/statement-fund-col-groups.model.ts::FundColGroupType" --json
codegraph refs "tools/api-inventory/src/analyzer/guards.ts::isGuardName" --json
```

| Symbol | Declared as | `definition.kind` | refs returned | Files in result | Ground truth |
| --- | --- | --- | --- | --- | --- |
| `ColType` | `export enum` | `type` | 2 | declaring file only | ~40 files reference it |
| `FundColGroupType` | `export enum` | `type` | 3 | declaring file only | imported by `statement-config.model.ts` |
| `isGuardName` | `export function` | `function` | 4 | `guards.ts` + `walker.ts` | correct |

All three report `resolution: "exact"`, `confidence: "high"`.

### The controlled comparison

`FundColGroupType` is the clean case, because it removes every other explanation:

```ts
// packages/shared/src/statements/models/statement-fund-col-groups.model.ts
export enum FundColGroupType { BreakOut = 'break-out', /* ... */ }

// packages/shared/src/statements/models/statement-config.model.ts  (line 9)
import { FundColGroupType } from './statement-fund-col-groups.model';
```

Same directory, direct relative import, no barrel, no path alias, no package boundary. Still
zero cross-file references.

`isGuardName` is imported exactly the same way and resolves:

```ts
// tools/api-inventory/src/analyzer/walker.ts
import { isGuardName } from './guards';
```

So the failing variable is the **declaration kind**, not the import style.

## What this rules out

Worth stating, because these were my first three hypotheses and all are wrong:

- **Not tsconfig path aliases.** The repo has 24 entries in `tsconfig.base.json` `paths`, but
  `FundColGroupType` is reached by a relative import and still fails.
- **Not `export *` barrel chains.** Same reason — no barrel is involved in the failing case.
- **Not workspace/package resolution.** Both files are in the same directory of the same package.
- **Not index staleness or a reduced backend.** A function in the same index resolves, and
  provenance claims `exact` / `high`.

## Suspected cause

`definition.kind` for `export enum X` comes back as `type`, not `enum`.

A TypeScript `enum` is unusual in that one declaration introduces **both** a type and a runtime
value. If the indexer classifies it as type-only, then reference collection likely runs only
whatever pass handles type positions, and the value-position uses (`ColType.Percent`,
`z.enum(ColType)`, `Object.values(ColType)`) are never attributed to the declaration. The two
intra-file hits that *are* returned look like the declaration site plus one same-file
annotation, which fits that theory.

Two candidate fixes, depending on how the extractor is structured:

1. Give `enum` (and `const enum`) its own kind, and register the declaration in **both** the
   type namespace and the value namespace, so existing value-reference collection picks it up.
2. If kinds are deliberately coarse, make reference collection for `kind: type` also scan value
   positions when the underlying declaration is an enum.

`enum` members are probably worth checking at the same time — whether `FundColGroupType.BreakOut`
resolves to the member, the enum, or nothing.

## Expected resolve path

For the `FundColGroupType` case the chain should be:

1. Parse `import { FundColGroupType } from './statement-fund-col-groups.model'` in
   `statement-config.model.ts`.
2. Resolve the relative specifier to the sibling module.
3. Bind the imported name to the exported `enum` declaration.
4. Attribute every use in that file — type positions and value positions alike — to that
   declaration.

Step 4 is where this appears to stop for enums.

For the broader `ColType` case, the same chain plus the parts I could not test because the enum
case fails earlier:

1. `import { ColType } from '@org-name/shared'` (or the `@org-name/shared/statements/models`
   subpath).
2. Resolve via `tsconfig.base.json` `paths` — `@org-name/shared` → `packages/shared/src/index.ts`,
   `@org-name/shared/*` → `packages/shared/src/*`. The npm workspace symlink
   (`node_modules/@org-name/shared` → `packages/shared`) is the fallback, but it points at
   `dist`, so the tsconfig mapping is the one that reaches source.
3. Follow the `export *` chain: `src/index.ts` → `./statements` → `./models` → `./statement-config.model`.
4. Bind and attribute as above.

Steps 2 and 3 are worth verifying independently once enums resolve, since a wildcard re-export
never names the symbol textually and needs explicit expansion.

## Why it mattered here

The question under investigation was whether `packages/shared` uses a set of enums outside one
subdirectory, in order to decide whether they could be moved into another package without
creating a dependency cycle.

Codegraph answered, in effect, "nothing outside the declaring file uses `ColType`", with high
confidence. Acting on that would have produced a circular dependency between
`@org-name/shared` and a contracts package. A plain text search found 13 files in
`packages/shared` alone.

The tool's own guidance — that missing edges do not prove absence — is what prompted the
cross-check. That guidance is doing a lot of work here; the `confidence: "high"` label pushes
the other way.

## Suggested reporting change

Independent of the enum fix: when a query returns only intra-file references for an **exported**
symbol, that is a strong signal of incomplete resolution rather than a genuinely unused export.
Either lower the reported confidence in that case, or add an advisory to the result. It would
have flagged this immediately.
