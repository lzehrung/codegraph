# Language coverage parity matrix

Semantic support targets correct results for ordinary code in every listed language, from syntax and facts proven in source. codegraph is not a compiler. When a result needs expression type inference, overload ranking beyond arity, generic constraint solving, or build-system membership, it returns `not_found` or `partial` coverage instead of guessing. The limits below name the known cases.

- Yes = supported and covered
- Partial = supported with intentional limitations
- No = not supported for that capability

## Capability notes

### Native parser and graph-only formats

- The native addon is required for source-language parsing and Tree-sitter queries. If it cannot load, Codegraph returns an error; it does not use a second grammar backend or reduced regex extraction. Files over the native size limit are skipped with `sourceTooLarge`, and native query failures report `queryFailure` without regex recovery. Document and stylesheet graph-only extraction remains supported.
- Registered queries target the grammar the native addon loads, and there is no per-language query rewrite layer for Kotlin or SCSS. Kotlin queries use `tree-sitter-kotlin-ng` node names, so a hand-written `codegraph grep --query` for Kotlin must use `identifier`, not `simple_identifier` or `type_identifier`. Kotlin references are not limited to call sites: `refs` on a property reports its non-call uses.
- Native parity fixtures cover extraction and end-to-end semantics for TypeScript, TSX, JavaScript, Python, PHP, Go, Java, C#, Rust, Kotlin, Swift, Zig, C, C++, Ruby, SQL, and Terraform. HTML, CSS, Less, Vue, and Svelte are covered for graph and specifier parity, and SCSS adds symbol, same-file navigation, and reference parity. Intentional non-results are locked by explicit `not_found` cases: HTML, CSS, Less, Vue, and Svelte navigation, document-format navigation, SQL column-level navigation, and ambiguous SQL basenames.
- Graph-only document formats do not claim semantic symbols or call hierarchy. A successful empty native query is an empty result, not a reason to recover with regex.

### Symbols and exports

- `locals` is file wide. `exports` is module scope: a name declared inside a function body, lambda, or closure is never published as an importable module symbol, including members of a type declared there. Go, Java, Kotlin, Python, Rust, Swift, and C/C++ all follow that rule, so function-local types, constants, and variables stay local while nested top-level types stay exported. Type members are published only for languages whose `exports` query captures them; TypeScript and JavaScript publish `export` statements, PHP omits methods, and Zig publishes file scope without a container's member functions.
- `getUndocumentedApiSurface` and `codegraph apisurface --undocumented` list local exports with no indexed docstring only in files whose leading comments can be checked. Verified capture covers TypeScript, TSX, JavaScript, Go, Java, C#, Kotlin, Rust, Zig, and SCSS. An exported TypeScript overload group counts as documented when any collapsed signature has JSDoc.
  JavaScript CommonJS function exports also retain leading JSDoc when the parser tree is available.
  Their target is the captured assignment function or, for an uncaptured TypeScript form, a definition at the export property; same-named locals do not inherit that comment.
- Python captures leading `#` comments, but not triple-quoted function/class docstrings, so the report conservatively leaves Python exports unchecked. PHP, C, C++, Ruby, Swift, SQL, and Terraform also export symbols without supported leading-comment capture. These files (and skipped source files without parser context) are excluded from `symbols` and named in partial `coverage.uncheckedFiles`; graph-only formats have no exported symbols in this report.
- Unused-export detection is not available. An internal prototype (`src/indexer/unused-exports.ts`) still reported used exports on this repository: worker entry points launched by path and helpers called through an object property.
- Method-like declarations are indexed as function locals wherever the grammar exposes named methods or member functions. Body edits map to the method local, and parameter edits set method-level `signatureChanged`.
- TypeScript, TSX, and JavaScript class fields (public and `#private`, with or without an initializer) are navigable `variable` definitions. Declaration-only `function_signature` overloads and named `namespace`/`module` declarations are symbols, `declare module "ambient"` is a namespace chunk, and a class `static` block is its own block scope, so a static-block `let` does not resolve from a sibling method. An aliased named import (`import { b as c }`) creates no phantom binding under the original name. A named function expression binds its own name in JavaScript, TypeScript, and TSX (`$scope.refresh = function refresh()`, `const f = function inner() {}`), including a named generator function expression; that name stays scoped to the function body, so it is neither exported nor resolvable from a sibling statement.
- Exported TypeScript and TSX declaration-only functions and named namespaces resolve through consumer imports, including `.d.ts`, `.d.mts`, and `.d.cts` targets. String ambient module names are not named exports.
- Java `record` and C# `record` (including `record class` and `record struct`) are `class`-kind symbols, and their base lists participate in type hierarchy like an ordinary class. Positional record components are indexed as variable locals in both languages, never as separate fields or accessors. Java and C# method, constructor, and record formal parameters are locals. A Java constructor declaration and the declared name of a `...` spread parameter are declaration names, so editing a constructor's name is a definition change rather than a reference to the class.
- C# indexes `struct`, `delegate`, fields, events, and properties as symbols, and local functions as file locals rather than exports. Constructors, destructors, operators, conversion operators, and indexers are not symbols: a constructor repeats the type name and would make the type ambiguous, and the others have no identifier name in the grammar.
- Swift indexes protocol `associatedtype`, `macro`, and `operator` declarations. `init`, `deinit`, and `subscript` remain semantic chunks rather than symbols: they have no identifier name in the grammar and repeat per type.
- Rust indexes `macro_rules!` definitions as function-kind symbols, and macro invocations resolve to the definition and contribute reference hits. Rust also indexes `type` aliases, trait associated types, and declaration-only trait methods. A trait method declaration and its impl definition are separate symbols with the same name, so a name-only lookup can be ambiguous.
- Ruby treats `Constant = Struct.new(...)` as a class-kind symbol with a synthetic detailed class declaration, and runtime-computed class factories stay outside that recognition. Compact `module Outer::Compact` and `class Inner::Tool` names are exports, so cross-file references to them resolve. `def self.x` singleton methods and `def foo=` setters are symbols.
- PHP symbols include declaration names, enum cases, constants, and declared properties. Namespace names and ordinary variable uses are excluded. Typed, untyped, and static property accesses navigate to their declarations. A `compound_statement` is a block scope, so a function declared inside another function is file-local and is never published as a module export.
- PHP dependency extraction keeps class, function, and constant imports in separate symbol namespaces even when their target text is identical. Symbol lists and compact and detailed graphs retain separate role-specific IDs and definition edges. `goToDefinitionById` and `findReferencesById` preserve the role.
- Go struct fields, `for ... := range` bindings, generic type parameters, and every name in a multi-name `const`/`var` spec are locals (`const (B, C = iota, iota)` captures `C`). Direct and promoted selector uses and range-variable uses resolve through go-to-definition and references. Extraction is query-driven and limited to declaration positions, so blank range identifiers and type-position names such as `int` are not indexed.
- C and C++ typedef extraction follows pointer, array, function, and parenthesized declarators without a fixed depth, and parameter type uses do not become extra declarations. Exports are not anchored on the file root, so declarations inside include guards, `namespace` bodies, and `template_declaration` are exported; a function body is what makes a declaration unreachable, and actual `static` storage classes are excluded. C++ prototypes are indexed like C prototypes, so a header publishes the same names under either grammar. With native captures but no syntax tree, pointer, array, and function-pointer typedef names survive, while C++ pointer-to-member typedefs still need the tree. Typedef reference recovery covers direct declaration use sites; macro-expanded uses are not claimed.
- C exports canonicalize function and tag redeclarations separately from typedefs and other ordinary names. `goToDefinition` and `findReferences` preserve the tag namespace through includes and local scopes, including same-spelled enum tags and typedefs. `resolveExport` accepts `cNamespace: "tag" | "ordinary"`; `preferredKind` alone cannot distinguish an enum tag from a typedef. Pointer, array, and function-pointer typedefs retain their own declaration ranges.
- C file-scope forward tags reuse included declarations, while block-scope forward tags can hide outer tags. Completed tags take precedence over incomplete declarations and retain preceding forward references. Compact and detailed symbol graphs retain separate tag and ordinary-name include aliases; expression and call lookup use the ordinary namespace.
- C++ also indexes out-of-line member definitions (`void A::f()`, `A::~A()`, `A& A::operator+=`), in-class declarations without bodies, nested namespaces (`namespace outer::inner`), explicit template specializations, concepts, unions, and preprocessor macros. The detailed graph connects an out-of-line definition to its owning class even when the class declaration is in an included header, and reads `static` or `virtual` from that declaration. C++20 module declarations (`export module foo;`) are indexed as class-kind symbols, including in module-interface files (`.cppm`, `.ixx`, `.mxx`); a first-party `import foo;` resolves to the declaring file like a `#include` with no resolution hint, `import std;` stays external, and a module declared in two files stays unresolved. Module partitions stay unsupported: `export module foo:part;` is indexed under `foo:part`, but the pinned grammar exposes only the `partition` field for `import :part;` and puts the primary name of `import foo:part;` inside an `ERROR` node, so neither form emits an import edge. Quoted and angle header units (`import "header.h";`, `import <header.h>;`) follow the same relative-first or configured-include-root resolution as the corresponding `#include` form, including when native capture is unavailable. A module specifier whose final component is a registered source extension (`a.b.c`, `a.b.cc`) is treated as a file path rather than a module name, because module names and header-unit specifiers share one shape. `preproc_include` and `import_declaration` both produce C++ dependency edges, and a function-like include macro (`#include HEADER("x.h")`) does not bind a neighbouring preprocessor identifier as the include path. The C++ grammar is pinned to the upstream revision that exposes the C++20 module nodes; no published `tree-sitter-cpp` release carries them yet.
- C++ same-scope callable resolution groups prototypes and definitions by parameter signature. It ignores parameter names and defaults. Call arity selects only one viable exact, default-argument, or variadic candidate; overlapping candidates remain unresolved without type-based ranking. References and detailed graphs connect equivalent declarations across included headers and source files, preserving calls and ownership edges.
- C++ parameter signatures adjust arrays and function types to pointers and discard proven top-level `const`/`volatile`; nested callback signatures treat `(void)` and `()` alike. Pointee qualifiers, references, inner array extents, and trailing member qualifiers remain significant. Qualifiers on opaque named types stay unchanged because an array typedef cannot be ruled out without type-alias expansion; unmodeled declarators remain conservative.
- C++ exports use their visible qualified names, such as `tools::run`. Namespace-level `using` declarations and inline namespaces add visible aliases; function-local `using` declarations do not publish exports. Invalid bare names do not become navigation results, references, or call edges. `ExportEntry.exportedAs` carries this visible name; `target.localName` remains the declaration's short name.
- C++ `using` aliases retain all canonical overloads for call-site selection. An alias inside an inline namespace is also visible through its enclosing namespace; a non-inline enclosing namespace remains required. Known argument counts are checked even for one callable, and same-signature functions in different namespaces stay distinct. Reference lookup uses the parsed language for C++ `.h` headers rather than assuming C from the extension.
- Impact call-compatibility hints can inspect a unique unqualified C++ function binding before checking its argument count. This retains mismatch warnings for invalid calls without returning those calls from `goToDefinition` or `findReferences`; shadowed names and ambiguous overloads remain excluded. Equivalent same-file prototypes and definitions share their accepted argument-count range, including defaults declared only on a prototype.
- A `.h` file parses as C++ when its first 8000 characters contain a C++ signal: `class`, `namespace`, `template`, `typename`, or `constexpr` used as a keyword rather than a plain identifier (`int class;` stays C), `operator` unless it is a plain identifier (`operator=` and `operator[]` still count), `using namespace`, a `using X = Y` alias, a `concept Name = ...` definition, a `co_await` expression, `::`, or an `import`/`export import` module line. Otherwise it parses as C.
- Include expansion preserves the parsed C++ identity of `.h` exports rather than assigning C tag namespaces from the extension. Qualified import handles remain usable with `goToDefinitionById`.
- A failed relative Python import keeps the specifier that was written. `from .missing import x` stays unresolved as `.missing` on file edges and in unresolved-import reports.
- Python discovers `.pyi` stubs alongside `.py` sources. Package imports resolve to `__init__.py`/`__init__.pyi` when present, otherwise to a PEP 420 namespace directory that contains an importable `.py`/`.pyi` member or subpackage; a directory with no Python content stays unresolved. Match-case captures in tuple, `as`, splat, and unambiguous bare patterns are local bindings, and qualified value patterns are not inferred as captures. `except E as err` and `with x as handle` bind the alias. Walrus assignments, tuple and list unpacking targets, PEP 695 `type X = ...` aliases, and `case Point(x=px)` keyword patterns are indexed. Static module-level `__all__` retains every string item, including an empty export set; function-local assignments, method calls, and comments do not filter module exports.
- Zig chunking emits function and `test` chunks.
- Zig `@import("api.zig")` resolves relative to the importing file. Only `pub` file-scope declarations are module exports; `export` alone provides C ABI visibility, not Zig module visibility.
- Declaration visibility filters module exports for the languages that declare it: Rust publishes every `pub` form except `pub(self)`, so `pub`, `pub(crate)`, `pub(super)`, and `pub(in path)` are exports and unmarked items and `pub(self)` stay file-local, including spaced spellings such as `pub ( self )`; Java hides `private`; C# hides `private` everywhere and `internal` at namespace or file scope, while an `internal` member inside a type stays exported; Kotlin hides `private` and `internal`; Swift hides `private` and `fileprivate`. Rust visibility is a per-file approximation with no crate or module lattice, so a sibling file can resolve a `pub(super)` or `pub(in path)` item that rustc would reject. A hidden declaration remains a file local, so same-file go-to-definition and find references still resolve it, and it does not bind through an import from another file, including a file whose declarations are all hidden. Languages with no visibility rule keep publishing every top-level declaration.
- Python module exports keep `__all__` and underscore filtering, and a module-level `from a import *` is an `exportStar` re-export, so `from b import name` resolves through it like an ECMAScript `export *`.

### Navigation and references

- Member selection keeps static and instance methods in separate inheritance lookup chains for JavaScript, TypeScript, TSX, Ruby, Swift, and Kotlin. In C++, Java, C#, PHP, and Python a same-named static member still hides an inherited instance member. `goToDefinition`, `findReferences`, and `buildSymbolGraphDetailed` use the same selection rule.
- C# and Java same-signature overrides hide ancestor methods before call arity is checked. A call whose surviving override cannot accept the argument count keeps navigation's unique-candidate behavior but adds no graph edge to the hidden ancestor; other inherited methods remain reachable.
- Find references reports ECMAScript named re-export declarations as non-executable API-surface references with `via.reexport: true`; consumers that need executable uses can exclude that marker. Star and namespace re-export declarations have no source-symbol token, while ECMAScript namespace-member uses resolve through visible aliases, including named and star-forwarded namespaces and renamed member exports at nested hops. Rename preview updates original-spelling namespace members reached through named imports without changing the imported namespace receiver.
- Find references reports each verifiable token in a resolved named or default import declaration. Source-side names use `via.importBinding: "imported"`, distinct aliases and default local bindings use `"local"`, and one token that serves both roles is returned once. Namespace and side-effect imports remain resolution context and are not claimed as per-symbol declaration references.
- In TypeScript, Python, and Rust, an imported module receiver gives way to a closer parameter or local with the same name. Go-to-definition, references, and detailed call edges exclude the imported member at shadowed uses while retaining unshadowed uses. In TypeScript and JavaScript, a local declared `typeof import(S)`, or only ever assigned `await import(S)` or `require(S)`, holds module `S` and does not shadow an alias of `S`.
- Receiver member navigation (`obj.method()`, `new Widget().size`) is implemented for every language whose member-access row declares receiver keywords: C++, C#, Go, Java, JavaScript, Kotlin, PHP, Python, Ruby, Rust, Swift, TypeScript, TSX, and Zig. `diagnostics.memberResolutionCoverage` reports exactly that set in `receiverAwareLanguages`, and every other changed-file language in `limitedLanguages`, meaning consumers reached only through a receiver expression may be missing from the ranked impact list. A keyword receiver (`this`, `$this`, `self`, `static`, `Self`) resolves against the enclosing type in all of them, including the languages where an unqualified member name also resolves. A supertype keyword (`super`, `base`, `parent`) never resolves against the current type: it walks declared class ancestors breadth first and returns only a unique shallowest match, so a same-named override in the deriving type is not reported. An interface or protocol listed beside the superclass in one base list (C#, Kotlin, Swift) is skipped, matching the language rule that the keyword names the base class. Python resolves `self` and `cls` members, including attributes assigned in `__init__`, unique inherited members walked breadth-first from declared bases, and locals assigned from a direct constructor call (`svc = Service()` or `svc: Service = Service()`); factory-assigned and unannotated-parameter receivers stay unproven. C++ is the one partial row: `this->member` resolves, while a value or pointer local (`Lib l; l.target()`, `Lib* p = new Lib(); p->target()`) is not yet a proven receiver and returns `not_found`.
- TypeScript/TSX, Java, C#, and Kotlin follow receiver chains through fields with declared resolvable types, including `this.middle.repo.find()` and a typed parameter's field; navigation, references, and detailed calls agree. Each field hop must be a unique proven member with an explicit type; unannotated or ambiguous hops remain unresolved, without inferring types from initializer expressions.
- Own-type keyword receivers traverse every declared member source in the shared ancestry table, including interfaces and protocols, PHP traits, and Ruby `include`/`extend`/`prepend` mixins. Detailed graph inheritance edges use the same table, so navigation and call-edge ancestry cannot drift into separate language models.
- An unqualified name inside a type body resolves against the type's own members only in Java, C#, Kotlin, Swift, Ruby, and C++. Every other language requires the member's receiver. Inside a Zig container a sibling member is reachable as `Self.helper()`, `@This().helper()`, or through an instance, never as a bare `helper()`: an unqualified call emits no edge and navigates to `not_found`, because container member names are not file-scope bindings.
- PHP method names use ASCII case-insensitive matching; properties and class constants remain case-sensitive. Class constants are static members. Import-role lookup distinguishes constructor and type operands (`instanceof`, `catch`) from arguments, even when class, function, and constant aliases have the same spelling.
- PHP import-alias `uses` edges follow the occurrence's class, function, or constant role. Class and function aliases fold ASCII case; constants require exact spelling. Different roles used in one function keep separate targets.
- C++ `using` declarations resolve function targets in directly included headers. Go-to-definition, references, and call edges preserve overload arity and local shadowing with cache off and with cold and warm disk caches.
- Implicit reference candidates and bare-name lookup share a source-unit relation: same directory and declared package for Go/Java/Kotlin, compatible declared namespaces for C# bare names, and same directory for Swift. Qualified C# names search all C# files in the same directory; references use the same candidate set. Each C# use still checks namespace visibility. C# partial declarations and Swift type/extension declarations share members only when their full owner identity agrees; nested C# owner identities include each enclosing generic arity. Swift `private` and `fileprivate` extension members, including members of a `private` or `fileprivate` extension, stay out of the shared owner when that owner is in another file; same-file private members remain visible. Proven-equivalent C# partial types also share one lookup target for callers outside the declaring parts.
- A Swift extension with a `where` clause shares members only with an extension of the same type whose constraint syntax tokens match. Spacing and comments do not affect that comparison. Its own members stay reachable inside the extension; it can use visible nominal and unconstrained-extension members. An unproven nominal receiver does not gain its members. Detailed call edges use the same source-only access without adding the constrained member to the nominal type. Different but logically equivalent constraints are not inferred.
- C# plain, `using static`, `global using`, and `using X = Y` directives, together with block- and file-scoped namespace declarations, are read from native Tree-sitter nodes. `goToDefinition`, `findReferences`, and detailed constructor edges preserve namespace visibility across reopened blocks, explicit namespace-qualified uses, and `using X = Namespace; X::Target`. Alias lookup respects its declaration scope, rejects unknown aliases, and gives each same-spelled alias declaration in a separate namespace block its own scope. A same-file internal type remains visible in its namespace; unrelated bare names and method-local shadows remain separate.

- A dotted use of a compilation-unit alias (`X.Type` after `using X = N;`) is unresolved for navigation, references, and graph edges inside a namespace whose enclosing chain declares a namespace or a type `X` without type parameters (a generic `X<T>` does not bind the bare name `X`), and it does not retry in outer namespaces. `X::Type` and member access on a parameter or local named `X` are unaffected. The alias check combines the declarations of the indexed C# files in the importer's project (its nearest `.csproj` directory, else the project root) when the lookup runs, except that a C# 11 `file` type counts only in its own file; a sibling project's `Local.X` does not shadow the alias. It applies to an alias under `#if`, `#elif`, or `#else`, leaves every such use unresolved while an indexed C# file of the project has no readable syntax tree, and does not check an alias declared inside a namespace.
- A C# name qualified through a generic type (`N.Outer<int>.Inner`) names a member of that constructed type, so navigation, references, and graph edges leave it unresolved instead of reading it as the type `Inner` in a namespace `N.Outer`; a nested type behind a namespace-qualified generic owner is a miss, not a wrong answer. Type arguments inside the name are names of their own and stay ordinary references.
- This relation does not read Maven/Gradle source sets, `.csproj` items, or SwiftPM targets. Same-package JVM files outside the directory and C# or Swift files in other directories produce `partial` coverage with `strategy_unavailable`. A JVM file without a `package` clause is its own unit: coverage is `complete` only when no other indexed JVM file can belong to the unnamed package and every JVM file could be read; otherwise it is `partial` with `strategy_unavailable`. The same rule applies to members of C# partial types and Swift types or extensions, because their other owner parts can sit in the same unproven files; a C# member also stays `partial` when a C# file in another directory could name its owner through a qualified path. Go package identity remains directory-exact. Existing export visibility limits still apply, including hidden C# and Kotlin `internal` declarations.
- A C# type declared outside every namespace in a file that also has block-scoped namespaces (`class Global {}` beside `namespace P { }`) is in the global namespace and visible to every namespace, while the file's namespace-scoped types keep their own visibility.
- C# namespace and partial-owner identities apply identifier equality to each path segment, so `namespace @P` and `namespace P` are one namespace. Namespace aliases use the same rule, so `using @X = P;` with `X::Target` (or `using X = P;` with `@X::Target`) resolves through navigation, references, and graph edges. A bare call inside a partial part resolves to a member declared in another part of the same owner; a static context reaches only static members, and a method-local function of the same name still wins. A C# 11 `file` type stays inside its declaring file for navigation, references, and graph edges, and same-named `file partial` owners in different files stay separate types. When namespace-qualified lookup finds multiple proven-equivalent partial C# type declarations, Codegraph chooses the deterministic representative by normalized file identity, then declaration source position.
- When several star imports expose the same simple name, each language's rule decides: Python lets the last `from m import *` win; Java, Kotlin, and Rust let an explicit import win (Java and Kotlin: explicit import, then same-package class, then wildcard; inside a class, a bare call to an inherited non-private method beats all three and a same-file top-level function, overloads are chosen across the whole class hierarchy (two surviving overloads, including a fixed-arity and a variable-arity one that both fit the argument count, or any two for a spread of unknown length, are ambiguous, because argument types are not ranked; C# binds to an applicable base overload when the derived type's same-named method does not apply), a private base method is not inherited (C#: `private` or no access modifier, but not `private protected`), and in a static context such a call has no target); Ruby constants loaded under one qualified path are one reopened constant; C and C++ declarations with the same callable signature are one function. Any other overlap is ambiguous: `goToDefinition` returns `not_found` and references report `partial`.
- A Kotlin wildcard package import considers top-level callable declarations from every file of that package when selecting an overload by argument count. Calls accepted by two candidates stay unresolved. Java and Kotlin package wildcards search both Java and Kotlin files in the package: Kotlin imports top-level package declarations, while Java imports only top-level package types, not Kotlin functions, class methods, enum constants, or nested types. Kotlin wildcards never import class or companion members. Disk and memory caches recheck the full package target set when a Java or Kotlin file is added. A Java top-level type without `public` is visible only in its own package, so a wildcard import from another package does not bind it.
- Java and Kotlin package wildcards retain detailed-graph bindings for each imported declaration's own file. Kotlin functions also retain uses of package functions; same-named declarations in another package are not imported.
- A use of a name declared later in the same scope is a reference when the language makes that declaration visible there (functions and classes; Python function-local assignment; JavaScript `let`/`const`, including the temporal dead zone). Variables follow point of declaration in every language; only hoisted forms (functions, classes, methods, and a Python function body looking up module names at call time) see later declarations. In C and C++, a name is visible only after its declaration, at file scope and in blocks; a prior prototype makes a later definition callable earlier, and class members are visible throughout the class.
- Go member access across packages resolves only exported (capitalized) names, both through a package selector (`pkg.Name`) and through a receiver of an imported type (`v := pkg.T{}; v.Method()`); such a receiver also produces call graph edges. Java hides only `private` across files; a package-private member called from another package (a compile error) is not rejected. A Ruby `class Inner::Tool` inside `module Outer` exports as `Outer::Inner::Tool` when an enclosing module in that file declares `Inner`, and as `Inner::Tool` otherwise; `class ::Top` is top-level. Kotlin type-name receivers reach only companion-object and `object` members. A nested Ruby class exports under its qualified path (`Outer::Base`), never as a bare `Base`.
- Coverage stays honest for uses Codegraph cannot place: a same-name use in a scanned file that resolves to more than one candidate (star imports, C++ overloads, or C++ `using` targets) or through an unproven receiver makes coverage `partial`. A name with no binding at all is proven unrelated by scope and does not. A classified receiver (`new Widget()`, a type name, `this`) proves a non-reference only when its type resolves, every supertype resolves, and that type does not declare the member. A member call on a local, parameter, field, or `this`/`self` is never a use of a free function, except in Kotlin and Go, where free functions can be called with member syntax.

- For non-SCSS definitions, any candidate or scanned file with an outermost Tree-sitter `ERROR` or `MISSING` range makes find-references coverage `partial` with `parse_error` and marks that file affected, regardless of the range contents. SCSS is exempt because its grammar reports `ERROR` on supported module syntax.

### Calls, call hierarchy, and call compatibility

- Receiver method invocations emit resolved `calls` edges, so `callers`, `callees`, and impact report method call sites instead of an empty set. Proven receivers are the type declaring the call (`this`, `$this`, `self`, `static`, `Self`, `cls`), a class `extends` ancestor (`super`, `base`, `parent`), a named indexed type used as a static or class-qualified receiver (`Example::shared()`, or `Cfg.load()` when `Cfg` is a class bound by an import or declaration), a local receiver whose constructor Codegraph already proves for `goto` (`const l = new Lib(); l.target()`), a struct literal (`Circle { r: 1.0 }.area()`), and a parameter or local with an explicitly declared type (`void use(Greeter g) { g.hello(); }`, `Box b; b.run();`). Fixtures cover TypeScript, JavaScript, PHP, Python, C#, Java, C++, Ruby, Rust, Kotlin, Swift, and Zig.
- A receiver method call is never resolved by matching the bare member name against module locals or import aliases, so `$this->helper()` inside a class is not attributed to an imported `helper` function. A member name that matches several declarations on one type is dropped unless the call's argument count singles one out. An unproven receiver emits no edge at all: a structural parameter type such as `value: { run(): number }`, a receiver assigned from a non-constructor expression (`auto b = Box::make()`), a generic type parameter, an unbound global such as `Math.max()`, or a local or parameter that binds the same name.
- Inherited `this`, `$this`, and `self` calls walk declared `extends`, `implements`, `trait`, and `mixin` edges breadth-first and record only a unique match at the shallowest level. An ambiguous name at that level emits nothing, even when a deeper type is unique. `super`, `base`, and `parent` follow class `extends` ancestors only.
- Go receiver method calls resolve: a `method_declaration` publishes a `member_of` edge to its receiver type, and a local proven by `GoBox{}`, `&GoBox{}`, or `var b GoBox` makes `b.GoHelper()` a resolved call. A same-named package function is never attributed to a method, and an interface-typed or factory-assigned receiver still emits nothing. Rust `impl Type`, `impl Trait for Type`, and generic `impl<T> Type<T>` methods are members of their self type, and trait default methods are members of the trait. Python `super().m()` and Ruby bare `super` inside `def m` resolve to the proven base class's member; an unresolved base stays unresolved. C has no methods on types, so a struct function-pointer call emits no receiver edge. `tests/receiver-call-edges.test.ts` locks all of these.
- Go-to-definition and the detailed graph agree on every call and construction site inside a callable: a resolved callee has a matching `calls` or `instantiates` edge, and a `not_found` callee has none. Exceptions: calls at module top level and computed callees such as `(a ?? b)()` have no graph caller or single target; a call that resolves to a parameter or a function-local binding (a callback) may have no edge; and a binding that holds a literal value (`const value = 1`) never gets a `calls` edge. One more difference is deliberate: a call whose known argument count the only candidate cannot accept still navigates to that candidate (so references and impact keep the callers of a changed signature), while the graph records no edge for it. Rare forms stay outside this agreement: a Zig member called through its type with an explicit receiver (`Self.helper(s)`), a parenthesized callee (`(f)()`), and a comment between a name and its arguments inside Rust macro arguments have no graph edge even when go-to-definition resolves them. A call through a nested TypeScript namespace chain (`A.B.f()`) resolves in neither go-to-definition nor the graph. Calls inside the arguments of standard expression macros such as `println!("{}", greet())`, `assert!`, and `vec!` (unqualified or through `std`, `core`, or `alloc`) are call edges; a member or path call inside macro arguments stays `not_found`. `macro_rules!` bodies and custom macro input are raw tokens until expansion, so `name(...)` inside them is not a call site. Module top-level calls have no graph caller.
- Call hierarchy follows only resolved `calls` edges between indexed callable symbols. Direct identifiers resolve through lexical scope at the use site, so nested declarations and local bindings shadow module locals and imports, and ambiguous or unproven bindings emit no edge. Public parity fixtures prove resolved direct calls with exact callsites for 16 fixture files: TypeScript, TSX, JavaScript, Python, PHP, Java, C#, Go, Rust, Ruby, Kotlin, Swift, Zig, C, C++, and Svelte inline scripts. Each fixture proves depth-1 outgoing hierarchy and one exact callee callsite. Svelte does not claim the rest of the symbol-navigation surface. Call hierarchy does not claim overload or virtual dispatch, trait or interface dispatch, function pointers, macros, reflection, dynamic sends, or name-only guesses, and `includeHeuristic` is accepted but adds no edges.
- Call compatibility hints compare changed callable arity with resolved callsites when parsing is high confidence. They are not type checking, overload resolution, trait dispatch, function-pointer analysis, macro expansion, or data-flow inference, and same-file overload sets are skipped. `analyzeImpactFromDiff` reports them through each changed symbol's `callCompatibility`. JavaScript, TypeScript, TSX, and JSX include callable variable arrows with parenthesized parameters and single bare parameters such as `const helper = a => a`. For C++, an in-class member prototype and its out-of-line definition are one callable: both changed declaration sites carry the same hints, and a default argument declared only on the prototype widens the accepted arity for both. Member callsites are attributed only through receivers Codegraph already proves for navigation, so same-named members of unrelated types and same-scope member overload sets stay without hints.
- C++ parameter packs accept zero pack arguments while fixed parameters remain required. Bare ellipsis and parameter-pack signatures remain distinct from fixed signatures, including nested callback types.
- `buildSymbolGraphDetailed`, receiver navigation, and impact signature extraction use shared accepted argument ranges. Default-last parameters, generic type commas, Java explicit receivers, C# extension-method `this` receivers, Ruby block capture, Rust trait signatures, and Kotlin spreads retain their language meaning. A C# extension method resolves through its declaring static class (`Ext.M(value)`, including alias- and namespace-qualified owners) or a bare call inside it, and those consumers count the `this` receiver as an argument there. Calls through the extended value (`value.M()`) need receiver-type inference and remain unresolved in navigation, references, and graph edges. Navigation can still identify a unique member whose call arity is invalid; that does not authorize a call edge.
- Python signature extraction distinguishes instance, class, static, and module functions rather than relying on `self` or `cls` spelling. `analyzeImpactFromDiff` selects receiver-inclusive arity for proven unbound instance calls and receiver-excluding arity for bound calls. Unknown spread lengths do not select an overload or produce a numeric mismatch hint.

### Type hierarchy and implementations

- Type hierarchy fixtures prove TypeScript and JavaScript `extends`/`implements` and abstract overrides, Java `extends`/`implements` including a `record ... implements`, C# base-list inheritance and interface conformance including `record class` and `record struct` base lists, Rust `impl Trait for Type`, Swift class inheritance and protocol conformance, C++ base-class clauses, Python class bases, Kotlin delegation specifiers, PHP `extends`/`implements`/trait use including enum interface conformance, Ruby superclass inheritance plus `include`, `extend`, and `prepend` mixin composition, and Go interface embedding plus struct embedding. JavaScript inheritance is read from the `class_heritage` node the JavaScript grammar emits rather than the TypeScript-only `extends_clause`, so a JavaScript subclass reports supertypes, subtypes, and implementations like a TypeScript one.
- Base-specifier extraction resolves only the direct base or interface type name. A generic type argument (`Base<Payload>` in TypeScript, C#, Java, Kotlin, Swift, and C++, `Base[Payload]` in Python) and a namespace or enclosing-type qualifier (`Ns.Base` or `Outer.Inner` in C# and Java, `Ns::Base` or `Outer::Inner` in C++ and Ruby) are excluded even when that segment names a real indexed class. Resolved `extends`, `implements`, `trait`, and `mixin` edges are emitted only when both declarations are indexed; external bases, structural or duck typing, runtime or metaprogrammed mixin composition, protocol extensions, overload dispatch, and name-only member matches are not inferred.
- C++ base lookup retains the qualified path, including `ns::Base` and `::ns::Base`. An absent qualified base does not fall back to a same-named unqualified class.
- Hierarchy implementation lookup supports interface or trait members and declared abstract or virtual override targets with proven implementers. It returns exact declarations, deduplicates inherited non-overrides, rejects ambiguous overload identity, and does not claim semantic support for graph-only document formats.

### Rename and refactor evidence

- Rename preview and refactor plans follow the indexed symbol, reference, call, and hierarchy capabilities above. They are not a compiler-grade rename for every source language. `rename.safe` is conservative and authoritative for the returned plan: unsupported dispatch, unresolved external symbols, ambiguous scopes, stale evidence, invalid live ranges, conflicts, and omissions keep it false or leave the site outside the plan.

### Duplicate detection

- Duplicate detection compares same-language units only and removes import declarations and directives before tokenization. Masking covers Astro and MDX module imports, embedded HTML, Vue, and Svelte script and style blocks, static Ruby `load` and `autoload` calls, Zig `@cImport` blocks, and Kotlin `import` nodes. Dynamic Ruby load paths, Zig non-import builtins, HTML document dependencies, and SQL object references stay in duplicate input. Rust masks only `mod x;` declarations, not inline module bodies. Parser-backed source units contribute AST-shape evidence; graph-first and text-only formats use text evidence.

### Imports and resolution

- Generic alias targets are not resolved through their type arguments: C# `using X = N.Box<int>`, C++ `using X = Y<int>`, Kotlin/Swift `typealias X = Y<Int>`, and TypeScript `type X = Y<string>` do not enable member navigation through the generic target. Member navigation returned `not_found` in probes for all five languages; navigating on the alias name returned `not_found` in C# and found the alias declaration in C++, Kotlin, Swift, and TypeScript.
- Ruby `require_relative "foo"` resolves from the requiring file's directory, never from a same-named file at the project root; `require "foo"` retains root/path-like precedence. Native import bindings and file edges agree on their target.
- TypeScript, TSX, and JavaScript named imports and re-exports that contain only `type` specifiers produce type-only file edges; mixed, empty, and side-effect clauses stay runtime edges. Other languages use their own type-only classification where available.
- Python imports nested in `if TYPE_CHECKING:` or `if typing.TYPE_CHECKING:` (including a one-line suite) are type-only bindings and file edges. `if not TYPE_CHECKING:`, the matching `else`, and other guards remain runtime imports; the guard must use one of those exact spellings.
- File dependency edges are deduplicated by physical source and target identity and by runtime versus type-only kind.
- Node `package.json#exports` condition matching follows author key order with mutually exclusive `import` and `require` modes threaded from ESM `import`/`import()` versus CommonJS `require()` and TypeScript `import x = require(...)`. Nested conditions, array fallbacks, and `default` termination match Node for those cases. Custom `--conditions`, `browser`, `types`, `development`, `production`, `deno`, `worker`, import attributes, and `#imports` maps are not modeled.
- JavaScript expands `module.exports = { ...source }` for statically resolvable CommonJS imports and local object literals, and unresolved spread sources remain explicit namespace-reexport markers. `module.exports = function () {}` and `module.exports = () => {}` export the module's `exports` binding. An assignment of the form `obj.prop = localVar` is not published as a module export.
- Native Python import bindings include parenthesized lists, comma-separated module imports, and line continuations, and comments inside import lists do not hide later names. Imports after same-line top-level assignments or calls remain module re-exports; conditional and function-suite imports do not.
- Native import-bearing queries (`graph.imports` and `graph.importBindings`) share one capture vocabulary: required `@stmt` plus path-bearing `@from`, with optional `@alias`, `@wild`, `@iname`, `@def`, `@ns`, and `@type_kw`. This union excludes the JavaScript CommonJS `module.exports` identifier capture (`@mod`) and duplicate-masking queries. PHP and Python module specifiers use the path-bearing native capture. Kotlin, Rust, and C# graph specifiers still use statement-text parsers to interpret native captures; PHP grouped `use`, `use function`/`use const`, and computed includes also use source text. These are native-path supplements, not reduced-mode recovery.
- Opt-in dynamic import heuristics (`graph.dynamicImportHeuristics` or `--dynamic-import-heuristics`) use shared constant-path folding and per-language trivia masks. JavaScript and TypeScript handle `require`/`import` with static `path.join`, `path.resolve`, and `new URL(..., import.meta.url)` forms; Python handles static `importlib.import_module(...)` and `__import__(...)` forms; Ruby handles `require File.join(__dir__, ...)`; PHP handles computed include/require paths rooted at `__DIR__` or `dirname(__FILE__)`. PHP computed includes can already resolve in native extraction, so the heuristic adds only new edges. Computed names and dynamic values are not inferred.
- The AngularJS heuristic for `templateUrl`, controller-name, and dependency-injection-token edges runs on every file the registry resolves as a JS-family language (`js`, `ts`, `tsx`, with `.jsx`, `.mjs`, and `.cjs` resolving to `js`). It applies only when a file reaches the module registry as `angular.module(...)` or `angular["module"](...)`; generic `controller` or `templateUrl` objects are not treated as Angular.
- Rust nested grouped `use` statements retain each module path and alias across comments and whitespace. Comments, raw strings, macros, and `#[cfg(test)]` items do not create fallback imports. Explicit `#[path]` targets are read from the declaring module's lexical scope, not from an importing or nested decoy, and inline modules use their own directory. Quoted and raw paths may contain `]`. Targets must stay within `--root`, and a missing explicit target does not fall back to a conventional sibling.
- Rust `#[path]` owner resolution walks the reachable module tree of the file's crate, built from Cargo crate roots, rather than scanning directories. Crate-root files resolve `mod foo;` against the directory that contains the root file, and raw-identifier modules such as `mod r#type;` walk `type.rs`. A `Cargo.toml` with `[workspace]` and no `[package]` contributes no crate roots. Every `mod` declaration stays distinct, so `cfg`-gated declarations of the same module keep each target reachable; when two reachable modules declare the same `#[path]` target and disagree on the parent, `super` resolution is suppressed rather than guessed. Files with no Cargo root, no crate root, no reachable declarer, or a truncated tree keep the earlier directory-scan behavior.
- Rust aliased re-exports (`pub use api::Bar as Baz;` and `pub use api::{Bar as Baz};`) publish the alias as the exported name and the original member as the source, and `pub use` re-exports resolve to first-party files before external classification.
- C# `using N;` imports the types of namespace `N` from every file in the importer's project that declares it, including a namespace split across many files and directories. Types of nested namespaces (`N.Inner`) and of other namespaces declared in the same files are not imported. A namespace-qualified name such as `N.Type` or `N.Type.M()` resolves when `N` names no local, parameter, or import: from the use file's directory, and from every directory that declares `N` when the file also has `using N;`. Without that directive, a qualified name whose namespace is declared only in other directories is not resolved. A `using` directive never binds a file in another language, even when its path matches the name (`using System;` beside a root `system.ts`).
- A plain C# `using N.T` binds the one file that declares type `T` in namespace `N`. An ambiguous or unreadable set stays unresolved instead of a path such as `N/T.cs`. The parts of one `partial` type count as one declaration, including parts in files with a mapped C# extension. A bare C# `using Foo` or Ruby `require "foo"` binds a same-named project file before an npm workspace package.
- C# alias `using X = Y;` contributes a dependency edge to `Y` and keeps `X` as the local alias, and `extern alias X;` is recognized as a local namespace alias that contributes no dependency edge. `global using` namespace, alias, and static forms are represented by the native grammar as `using_directive` and preserve dependency edges plus import bindings. A namespace alias (`using X = Some.Namespace;`) resolves to the first-party files that declare that namespace in block or file-scoped form. `X::Target`, `Some.Namespace.Target`, and `global::Some.Namespace.Target` resolve in type and constructor positions against declarations in the same directory, even when the use file declares unrelated namespaces. Dotted member access through the alias (`X.Type.Member`) still depends on a single-file resolved alias binding. A namespace split across files keeps the alias unresolved while still contributing a dependency edge to every declaring file, and a namespace with no first-party declaration, such as `using Col = System.Collections.Generic;`, stays external. While a C# file of the importer's project (its nearest `.csproj` directory) has no readable syntax tree, `X::Type` and `X.Type` stay unresolved for navigation, references, and graph edges, because that file may declare the same type; the alias keeps its dependency edges. The answer comes from the current index, not from the cached importer, so it follows the file's recovery.
- Java and C# type-qualified calls (`Util.Two(1, 2)`) choose among the type's same-named static methods (in C#, across every part of a partial type) by argument count; a method group (`Util.Two`) or a count that several overloads accept stays unresolved. Go-to-definition on an overload's own declaration in C#, Java, Kotlin, or Swift opens that declaration.
- C# `using static N.T;` binds to the one file that declares type `T` in namespace `N`. A bare name then resolves to an accessible static member, constant, or nested type of `T` in go-to-definition, references, and call graphs, after the enclosing type's members. Instance, extension, `private`, `protected`, and `private protected` members are not imported; `internal` and `protected internal` members are. Overloads from several directives merge and are chosen by argument count. A name that two directives, or a directive and a namespace member, both provide stays unresolved. Only a type with that namespace and name is the owner: another same-named type, even in the same file, contributes nothing. A type split across partial declarations in several files, `global using static`, and nested types (`using static N.Outer.Inner;`) are not bound.
- PHP reads Composer PSR-0, PSR-4, classmap, and `autoload.files` metadata for first-party resolution, but Composer autoload machinery never becomes an implicit dependency-graph edge.
- Ruby `load` and `autoload` are file dependencies alongside `require` and `require_relative`. The `.rbw`, `.rake`, and `.gemspec` aliases use the same standard-library classification as `.rb`, so `require "json"` is not an unresolved-import finding.
- Registered extension aliases are discovered and indexed, and an explicit link or include path to one resolves (`<a href="page.xhtml">`, `include 'partial.phtml'`). Extensionless module resolution keeps each language's importable extensions, matching the language runtime: `import util` does not resolve to `util.pyw`, and `require_relative "helper"` does not resolve to `helper.rbw`.
- First-party resolvers confine hits with a physical realpath check against `--root` while keeping the logical path for output, matching Rust `#[path]`. Java, Kotlin, C#, PHP, and Python symbol indexes start at the nearest language manifest file when one exists (a directory whose name matches `*.csproj` is skipped) and otherwise the project root, so a same-named package in a sibling workspace does not bind. A directory is a file edge only when the language runtime treats it as a module (Python `__init__.py`/`__init__.pyi` packages, PEP 420 namespace directories, and Go package directories); otherwise the resolver tries the language index file or returns nothing. A leading U+FEFF is stripped from tsconfig JSON and other resolution source text so BOM-prefixed `tsconfig.json` still supplies `paths`. A directory named `tsconfig.json` is not a config file.

### Stylesheets and single-file components

- SCSS uses the native addon for import and specifier extraction. Symbol extraction covers `@mixin` and `@function` names as `function`-kind symbols and `$variables`, placeholder selectors, class selectors, and id selectors as `variable`-kind symbols. Go-to-definition, find references, and rename preview resolve same-file declarations and uses, and Sass module members across files. Stylesheet star imports expand only from explicit exports, never from the locals fallback, so an `@import` does not invent named bindings for every class selector in the imported sheet. CSS and Less have no symbols by design.
- SCSS module loads: `@use` binds the default namespace (the URL's last segment, without a leading `_` or extension), an `as` alias, or `as *`. Namespaces compare as written, so `my_lib` and `my-lib` differ; variable, mixin, and function names treat `-` and `_` as the same character, while a placeholder name compares as written (`%a-b` and `%a_b` are two placeholders). `@forward` re-exports public members, including `as prefix-*`. Its `show` and `hide` lists name the exposed (prefixed) members, and a bare name selects mixins and functions, never variables. `@import` merges members into the global scope, has no privacy, and brings in what the imported file `@forward`s or `@import`s. A `@use` of a file that `@import`s sees those imported members. An `@import` runs the imported file inside the scope of its importer, so a partial reads the variables, mixins, functions, and placeholders that its importers declared or imported, and the `@use` namespaces of its importers; the order of the imports is not modeled, and a name that two importers define differently stays unresolved. A file loaded with `@use` or `@forward` has no such scope. A directory loads its `_index.scss` or `index.scss`. A warm incremental rebuild that cached an unresolved `@use "lib"` re-resolves that importer when `lib/_index.scss` or `lib/index.scss` is added. A directory whose name starts with \_ is included: `@use "./_theme"` loads `_theme/_index.scss`. An `@import` loads the first tier that exists: a file import-only sibling (`_name.import.scss` or `name.import.scss`), then an ordinary file (`name.scss` or `_name.scss`), then a directory import-only index (`name/_index.import.scss` or `name/index.import.scss`), then a directory index (`name/_index.scss` or `name/index.scss`). A directory import-only index does not override an existing file. `@use` and `@forward` never load an import-only file. Two siblings in one tier leave the `@import` unresolved, with `partial` coverage. An `@import` inside a rule or an at-rule block declares what it imports in that block only; this scan does not follow blocks, so a use of such a name is `not_found` and the coverage of the imported file is `partial`; a placeholder it declares stays visible to every `@extend`. Plain CSS imports (`.css`, `url(...)`, `http://`, and imports with a media query) are not loads. `sass:` modules stay external.
- SCSS names: a name that starts with `-` or `_` is private to its module under `@use` and `@forward`; only a `with (...)` key can still configure a private `!default` variable. Parameters, `@each` and `@for` variables, `using` parameters, and keyword-argument names are local, so they never name a module member. A parameter hides a member from the end of its own default value to the end of the body: its default reads the member of the same name, and the default of a later parameter reads the parameter. A variable declared in a block hides the member after its own statement; each assignment of a block variable is its own definition, and go-to-definition names the nearest one. A variable that one file assigns again stays one variable, also when the assignment sits in a top-level `@if`, `@each`, `@for`, or `@while`: go-to-definition resolves to the first assignment, and find references lists every assignment and use. A file-scope flow assignment after `@import` (`@import "vars"; @if true { $x: 2; $x: 3; .a { w: $x; } }`) joins every reassignment and the reads in that flow to the imported variable when exactly one import declares it. A provisional binding is not a loop local, so it does not hide the next assignment. `@each $x` and `@for $x` stay locals, and assigning that loop variable is not joined; assigning a different name inside the loop still is. Several matches or an unresolved import leave the name unproven and coverage `partial`, and no match keeps the block local. A file-scope flow assignment after `@use ... as *` is a new local: Sass does not assign the star-loaded variable and the local does not escape the flow block, so an outer read stays a reference of the module variable and rename leaves the local alone. A top-level assignment, or `!global`, does assign that module variable and stays `partial` because the two declarations are not joined. An assignment inside a rule does not update the imported variable unless it uses `!global`. A comma inside a square-bracket list does not start a parameter (`@mixin box($values: [1, $size])` has no `$size` parameter). An eager call or include that appears before a function or mixin is plain CSS, not a reference of that later declaration, unless a preceding `@use ... as *` or `@import` already supplies the name. A mixin or function declared inside a block hides a module member of the same kind and name from the end of its name until that block ends, so the include or call is not a reference of the outer member; a use before the declaration still is. Find references on the scoped callable lists its declaration and the bare calls or includes of the same kind inside that scope, treating `-` and `_` as the same character. The nearest such callable owns the use. Go-to-definition and position-based find references name that indexed scoped mixin or function, including a `-`/`_` spelling; a covering callable with no indexed symbol stays `not_found`. A namespaced use, a use of the other kind, and a use outside the block are not references of the scoped callable. A dynamic lookup in that span may still name it: `function-exists`, `get-function`, or `call` for a function, and `mixin-exists` or `get-mixin` for a mixin, through a proved `sass:meta` binding or as a legacy bare built-in, with `-` and `_` the same character. Those proved calls and includes stay references; coverage is `partial` and rename is unsafe because the lookup string is not edited. A lookup outside the block, or one a proved user function owns, does not. A call inside a mixin or function body, including a parameter default, is deferred: when that declaration is later in the file, coverage is `partial`. An interpolated placeholder declaration (`%btn#{$suffix}` or `#{$prefix}%btn`) is not the static placeholder of its text prefix. A member is configurable when any top-level assignment uses `!default`, so `$x: null; $x: 1 !default` accepts a `with` key. An assignment to a loop variable (`@each $x`, `@for $x`) changes that loop variable, not the file variable of the same name. A selector pseudo-class that takes arguments (`:is(`, `:not(`, `:where(`, `:has(`, `:nth-child(`) is no function call. A pseudo-class inside `selector(...)` in an `@supports` head is CSS too; a call in an at-rule expression (`@if has(1)`) stays a call. Strings and comments inside the `#{...}` of a quoted string or of an unquoted `url(...)` are text, while the expression stays code. An unquoted `url(...)` inside `#{...}` is opaque, so `//` in `#{url(http://example.com/x.png)}` is not a comment. A custom property value (`--name: value`) is literal CSS, so a `$name` in it is no use; only `#{...}` interpolation is code. A complete escape, including a hex escape of up to six digits and its optional whitespace, is consumed before a `}` or `;` can end the value, so `--close: \}` does not close the rule and a following block variable stays local. In a CSS `@import`, the media query and the interpolation in `url(...)` are read, and a quoted URL is raw text. Placeholders are not namespaced members: `@extend %placeholder` resolves in the same file or in a module loaded upstream, and every target of an `@extend` list counts. A placeholder counts wherever its rule sits: in a media query, in another rule, or in a mixin body. A file that declares one name more than once (also in nested rules) has one placeholder: go-to-definition names the first declaration, find references lists every declaration, and a rename edits them all. Two files that declare the name leave the use unresolved, with `partial` coverage. A placeholder in the middle of a compound selector (`.a %ph .b`) has no index symbol, so it is no navigation start, but it stays a site of a placeholder of the same name that the file declares elsewhere. A click on the namespace (`b` in `b.$brand`) stays `not_found`.
- SCSS reference coverage is `partial` for an unreadable file (a consumer that the graph knows stays a candidate), an unresolved `@use`, `@forward`, or `@import` URL (a directory name that may reach the declaring `_index.scss` counts), a Vue or Svelte style block that may load the module (through the declaring file, or through a file that forwards or imports it), more than one matching member (a mixin or function declared twice, a variable that two files declare in one scope, or a partial whose importers define the name differently), a file of the same `@import` scope that declares the name again (it assigns the same variable or replaces the same mixin or function), a file that assigns a variable that a module it loads with `@use ... as *` also declares (Sass assigns the variable of that module, so one variable has two declarations), a deferred call or include whose function or mixin is declared later in the file, a file-scope flow assignment that may change an imported variable, an interpolated placeholder declaration, and dynamic `meta.load-css`, `meta.get-function`, `meta.get-mixin`, `meta.module-variables`, `meta.module-functions`, `meta.module-mixins`, `meta.variable-exists`, `meta.global-variable-exists`, `meta.function-exists`, and `meta.mixin-exists` (each with `-` or `_` in its name; the namespace of `sass:meta` compares as written). A bare `get-function`, `call`, `variable-exists`, `global-variable-exists`, `function-exists`, or `mixin-exists` (either `-` or `_`) with no `sass:meta` load is dynamic too, unless a user-defined function of that name is already declared in the file or proved in another file; a later declaration does not own the earlier call. The same names called through a proved `sass:meta` binding are dynamic. A namespaced call or include through a module that `@forward`s `sass:meta`, including through another `@forward`, is the same kind of lookup (`helpers.get-function("pad")`, with `-` or `_`): that file's references are `partial` and rename is unsafe. A call through a namespace that does not forward `sass:meta` stays an ordinary member. `@forward` of a built-in module leaves the forwarder's exposure incomplete, so a name it cannot prove is unproven rather than absent. `variable-exists` also names a block local in its scope, so that local's coverage is `partial` and rename is unsafe; `global-variable-exists` does not see a block local. `function-exists`, `call`, and `get-function` do the same for a scoped function where it is visible, and `mixin-exists` and `get-mixin` for a scoped mixin; a lookup outside that block does not. A same-file function declared before the call owns it even when `sass:meta` was loaded with `as *`. A same-kind callable already declared in the file, at the top level or inside an open block, owns a bare call or include of a `sass:meta` name before that call is classified as a lookup, including non-legacy names such as `get-mixin` and `load-css`. A later declaration does not own the earlier use, and a namespaced `meta.load-css` stays a lookup. The graph has no edge for a `@use` inside an Astro `<style>` block, so such a consumer is neither read nor reported.
- SCSS rename preview edits only the member name (not the namespace or a forward prefix) and updates `show`, `hide`, and `with` entries. It reports `name_collision` when a scope that sees the member already declares or exposes the new name: the declaring file including private names, a module that forwards it (under every prefix), and an `@use ... as *` or `@import` scope; a placeholder collides with any placeholder of the new name that a file seeing it can extend. A new name without a sigil is checked in the spelling the edit writes (`y` for `$x` is `$y`). Block variables and scoped callables compare `-` and `_` as one character. A private name that takes a public name is checked against the scopes that then see it through `@use ... as *` and `@forward`. It reports `shadowing` when a scoped variable, mixin, or function would capture a bare same-kind use after the rename, judged by the name the use has there (the forward prefix plus the new name); a namespaced use cannot be captured. Renaming a scoped mixin or function to an imported same-kind name likewise reports `shadowing` at bare calls within its scope that would switch from the module member to the local callable; calls before its declaration, outside its block, or through a namespace do not collide. Each bare call or include that the scoped callable already owns is also `shadowing` when a different same-kind scoped callable would own that use under the new name (`-` and `_` equivalent); a callable of that name in a block that does not contain the use does not. Renaming a scoped mixin or function to a `sass:meta` or legacy lookup name (`get-function`, `call`, `get-mixin`, `load-css`, the `module-*` lookups, the existence predicates, or a `_` spelling) is `shadowing` when a bare dynamic call of that name is visible in its block, because the call would invoke the renamed callable. A namespaced call and a call outside the block do not. It reports `invalid_identifier` when a new name that starts with `-` or `_` would hide the member from a use through `@use` or `@forward`, or when a `@forward` `hide` list names the new name (with the forward prefix, `-` and `_` equivalent) and a use reads the member through that forward; a `show` or `hide` entry that already spells the new name is not edited with the member, so a `show` list can newly expose it and that exposure is checked for `name_collision`; the declaring file, `@import`, and `with` keep access to a private name, and the `show` and `hide` entries that name the member are renamed with it.
- SCSS parse-error ranges do not affect reference coverage: the pinned tree-sitter-scss grammar emits ERROR nodes for supported module syntax that src/scss/ reads and proves; revisit after the planned grammar fork.
- The pinned SCSS grammar leaves `@use as`, `@forward as`/`show`/`hide`, and namespaced names as ERROR or plain values, so those forms are read from source text; file targets still come from the indexed stylesheet edges. A `//` comment ends at the line break and is read before quotes, and an unquoted `url(...)` is one token, including inside `#{...}`, so an apostrophe in a comment or `url(http://...)` hides no declaration. A hex escape inside that token, such as `url(http://cdn/a\20 b.svg)` or `url(\68 ttp://example.com/x)`, stays in the token, so the code after it on the line is not a comment. An interpolation in a loud comment reads its expression without changing the following statement or enclosing argument context.
- SCSS conservative limits: a block variable with Sass-equivalent but differently spelled `-`/`_` hides the module member, but go-to-definition returns `not_found` rather than trust an exact-name scope fallback. The module member's references omit that use and stay `complete`; the block local's references are `partial` (`name_equivalence_unavailable`) and rename is unsafe. A nearer block local with the same Sass name and a different `-`/`_` spelling owns a read of the outer variable (`.a { $foo-bar: 1; .b { $foo_bar: 2; width: $foo-bar; } }`), so find references of the outer variable omits that read and is `partial` (`name_equivalence_unavailable`). A read no nearer equivalent binding covers stays a reference of the outer variable and can stay `complete`. Rename of a scoped mixin or function edits those bare calls and includes and is safe when the new name captures nothing, no edited reference would be owned by a different scoped callable, and no dynamic lookup in its block may name it (`function-exists`, `get-function`, or `call` for a function; `mixin-exists` or `get-mixin` for a mixin; a proved `sass:meta` binding or a legacy built-in; `-` and `_` equivalent). The lookup string stays unchanged, so rename is unsafe. A lookup outside the block does not count. A call the reference walk still omits stays `unresolved_reference`. When the declaring file cannot be scanned, the scoped callable's coverage is `partial`. An interpolated `@extend` name, and an interpolated placeholder declaration, are not static placeholder references; reachable placeholders report `partial` coverage and unsafe rename. Dynamic `sass:meta` calls require a proven module binding (including one inherited through `@import`, and a namespace whose module forwards `sass:meta`), while a project module named `meta` remains navigable. Existence predicates (`variable-exists`, `global-variable-exists`, `function-exists`, `mixin-exists`, and their `_` spellings) are the same kind of lookup, through that binding or as a legacy built-in unless a user function is proved to own the call. Legacy `call("name")` is the same kind of lookup. Interpolation in a loud comment (`/* #{...} */`) is a use; a `//` comment is not. Outside a string, a backslash escapes the next character, so an odd number of backslashes before a dollar sign is literal CSS and an even number is a variable. A namespaced call such as `lib.url(plain)` or `lib.url($arg)` is a function call, not an opaque CSS url.
- CSS, SCSS, and Less resolve imports against stylesheet extensions only, including Sass partials for extensionless and explicit `.scss` specifiers and non-canonical extension casing. Graph-only CSS handles media-qualified imports, and graph-only Less handles option-qualified imports. CSS Modules `composes ... from` and `@value ... from` produce stylesheet dependency edges.
- Stylesheet import bindings use the same relative-first resolution as file edges, including bare quoted paths and SCSS partials. A source specifier may bind a partial; a document `url()` does not. JavaScript and TypeScript bare imports keep package resolution.
- Vue and Svelte index embedded script, template, and style blocks through the JS/TS, HTML, and CSS-family supports, so their standalone grammars are not on the indexing path even though the native addon ships them. Single-file-component block scanning matches nested same-name `<template>` blocks by depth, and a malformed document stops block parsing at the first unmatched opening tag rather than reclassifying content inside an unclosed block.

### Document and template formats

- Markdown, MDX, Astro, Handlebars, reStructuredText, and AsciiDoc are graph-first. They use shared text extraction for document links and format-specific include or import syntax, and they intentionally do not claim semantic chunking, navigation, references, or native-addon parity.
- HTML document graph extraction ignores HTML comments and `<pre>`/`<code>` literal blocks, and includes static attributes, inline scripts, and inline `<style>` `@import`/`url()` references. Scanning is quote- and context-aware: comment openers and literal-block openers apply only outside quoted attribute values and `<script>`/`<style>` bodies, so a `<!--` or `>` inside an attribute value or script string never suppresses later real edges. Query-driven `href` is captured only from `link` and `a`, and `src` only from `script` and `img`; the graph's asset walker still reports media-element sources. Native HTML tag and attribute checks are case-insensitive, including mixed-case imports and `id` names.
- Every document format walks embedded HTML through one shared extractor driven by a per-format table, which runs the attribute walk, the inline `<script>` pass, and the inline `<style>` pass, so identical markup yields identical edges wherever it is recognized. HTML, Astro, and Handlebars enable all three passes. Each opt-out names the tag, attribute, or pass it omits and carries a reason, and a test asserts that every omission is named, so an opt-out cannot flip silently.
- Markdown and MDX walk the same embedded HTML forms as HTML, alongside markdown links and autolinks, and still ignore HTML comments, front matter, images, and code blocks. They opt out of `img` because Markdown image syntax is deliberately not a dependency edge, so a raw `img` element is not one either, and out of `source` srcset candidates because those are image sources covered by the same exclusion. A `source src` is ordinary media (`<video><source src="./clip.webm">`), which HTML itself reports, so it stays an edge.
- AsciiDoc walks the same embedded HTML forms after its `include::`, `xref`, `link`, and anchor references, and still skips `ifdef`/`ifndef`/`ifeval` regions and listing or literal blocks. It opts out of `img` and of `source` srcset candidates for the reason that applies to AsciiDoc inline image syntax, while a `source src` stays an edge.
- Handlebars walks the same embedded HTML forms as HTML, plus static `{{> partial}}` and block `{{#> partial}}` references. Interpolated paths such as `href="{{dynamicPath}}"` are ignored.
- Astro walks the same embedded HTML forms as HTML, so a scoped `<style>` block's `@import "./theme.css"` and `url(./bg.png)` become document edges like HTML, Vue, and Svelte. Frontmatter static imports use the script candidate order, while its HTML-style links use document candidates.
- reStructuredText keeps its directive-based extraction (`include`, `literalinclude`, `toctree`, `:doc:`) and runs no HTML pass: its HTML appears only in `raw:: html` bodies and inline literals, which the directive model does not separate. It still ignores comments and literal or code blocks and skips wildcard `toctree` entries; `:ref:` and `:term:` target in-document labels and are not extracted.

### SQL

- SQL is supported as a repository language, not a full database analyzer. It discovers `.sql` files by default, chunks statements including T-SQL `GO` batches while retaining `BEGIN`/`END` bodies, extracts table, view, index, and routine symbols, records common DDL and DML plus nested CTE read and write facts, creates SQL-to-SQL object edges, and supports SQL-file go-to-definition and find-references.
- Object resolution is conservative everywhere it is used, in object edges, navigation, and `explain`: an exact object name wins, and an unqualified basename resolves only when exactly one definition carries it. Ambiguous basename guesses are skipped, and no current schema is inferred from migrations, seeds, dumps, or fixtures.
- SQL navigation resolves schema-qualified names plus object-level `alias.column`, `table.column`, and `schema.table.column` references to table and view definitions when the prefix identifies one indexed source. An implicit table qualifier can follow an exact schema-qualified `FROM` source even if another schema defines a table with the same basename. Quoted identifiers retain their case. Specific column definitions are not resolved; native semantic parity covers that limitation with an explicit `not_found` case. A qualifier that names a routine called in a `FROM` list, such as `get_users` in `SELECT get_users.id FROM get_users()`, belongs to that routine and resolves to no table of the same name.
- Routine-source and relation aliases use their enclosing `SELECT` scope, including nested queries: an inner routine-result alias cannot hide an outer table alias, and an inner relation alias can shadow an outer routine alias. When a routine and relation share an alias in one query, go-to-definition returns `not_found` and find-references reports `partial` coverage with `strategy_unavailable`; nested `EXISTS` and `JOIN` relation sources contribute read and join facts without treating expression-level `FROM` as a source.
- Routine calls are references to the routine. Go-to-definition and find-references follow `name(` and `schema.name(` in queries, column defaults, and `CHECK` and index expressions, `CALL name`, T-SQL `EXEC name` and `EXECUTE name`, `EXECUTE FUNCTION name()` in `CREATE TRIGGER`, and calls inside a `$$` body (SQL and PL/pgSQL only) or a `BEGIN`/`END` body. `DROP`, `ALTER`, `COMMENT ON`, and `GRANT ... ON` statements that name a routine are references too, as `DROP TABLE` and `ALTER TABLE` are for tables, and a target list such as `DROP FUNCTION f(integer), g` names every routine in it. Rename preview lists the same sites and edits the name in a qualified reference, so `public.f` becomes `public.g`; a bare reference to a schema-qualified definition is an unsafe site. Impact follows the same calls through `sql:*` edges.
- A call resolves only to an indexed `CREATE [OR REPLACE] FUNCTION` or `PROCEDURE`, so built-ins such as `lower(` resolve only when the project defines that routine. Explicit routine syntax (`DROP FUNCTION`, `ALTER FUNCTION`, `CALL`, `EXEC`) with no such routine gives `not_found` from go-to-definition and `refs`, with or without other routines indexed, and never resolves to a table of that name. A schema-qualified call matches the same schema or an unqualified definition, never another schema. A same-named column or table without call parentheses, a name inside a string, comment, or quoted identifier, an alias column list such as `FROM generate_series(1, 3) g(i)`, T-SQL table hints such as `FROM users (NOLOCK)`, an `INSERT`, `REPLACE`, or `COPY` target, with or without a modifier such as `IGNORE` or `TOP (n)`, the variable of a PL/pgSQL `EXECUTE cmd`, and a `$$` body in another language such as `plpython3u` are not calls. Functions and procedures, triggers, and tables have separate name spaces, so a trigger and the function it runs can share a name.
- A routine name that two definitions carry, such as overloads, a repeated `CREATE OR REPLACE`, or one name in two schemas, cannot be tied to one definition. Go-to-definition returns `not_found` for a call, and `refs` reports `partial` coverage with `strategy_unavailable` and the affected files. Overloads are not ranked by argument count. Other `CREATE` forms such as `CREATE OR ALTER`, `DEFINER` clauses, and temporary functions are not indexed, and dynamic SQL such as `EXECUTE format(...)` is not scanned: the command string is text, and only a call in the expression that builds it is found.
- Call scanning reads PostgreSQL and SQL Server lexing: block comments nest, `E'...'` strings take backslash escapes, and a `[` after `ARRAY`, `)`, `]`, a quote, or a word that is no keyword or number opens a subscript, while any other `[` opens a T-SQL identifier. Statement splitting reads nested comments the same way, unless nesting would leave one open, which marks MySQL or SQLite text and ends each comment at its first closing delimiter, although a later `*/` in such text, even inside a string, can still close the nesting; inside a statement, table and view facts still end a comment at its first closing delimiter. Statement splitting also honors PostgreSQL `E'...'` and `e'...'` backslash escapes, so a semicolon in such a string is not a boundary; MySQL backslash escapes in plain strings are not read. A `[...]` list literal (DuckDB, BigQuery) or a spaced subscript such as `arr [1]` reads as an identifier, so a call inside it is missed. A PostgreSQL `EXECUTE name` of a prepared statement outside a `$$` body reads as a T-SQL call, and an `INSERT` without `INTO`, or after a modifier such as `IGNORE` or `TOP (n)`, records no table write. A column named `call`, `exec`, or `execute` that is aliased without `AS` reads as a `CALL` unless it directly follows `SELECT`, `DISTINCT`, a comma, or an opening parenthesis, with only whitespace and comments between them.
- Block keywords are bare tokens, classified with the shared bare-keyword check and one trivia table per scan. `t.case`, `t . case`, a comment between the dot and `case`, `@case`, a quoted name, and a decimal such as `CASE .5` are not keywords, and `--` inside a string is not a line comment. Only bare `BEGIN` and bare `CASE` open a frame. `END IF`, `END LOOP`, `END WHILE`, `END REPEAT`, and `END FOR`, with an optional identifier label and then `;` or the end of the text, close nothing, so `LOOP` ... `END LOOP`, `REPEAT` ... `END REPEAT`, a labeled loop, and a procedural `CASE` that contains `LOOP` stay inside the routine. `END CASE` closes the innermost `CASE`. Any other `END`, including T-SQL `END IF @x` with no semicolon after `IF`, closes the innermost `BEGIN` or `CASE`. A `GO` on its own line ends the batch and clears open frames. A column or parameter named `loop`, `repeat`, or `while` does not swallow the next statement.
- Bare SQL keywords, not variable names such as `@update` or dotted components such as `u.select`, delimit query scopes and source clauses. T-SQL `CREATE TABLE` computed columns of the form `column AS routine(args)` record a routine call; column types, `CAST(... AS type)`, SELECT aliases, and call-shaped `ON CONFLICT`, `OVER`, `FILTER`, and `WITHIN GROUP` clauses do not. Those names remain valid routine names at actual call sites such as `SELECT conflict(id)`.
- SQL PR impact mapping is object level. A changed `CREATE TABLE users` becomes a changed symbol, and only files that read that object are impacted, with a symbol-level `directRef` reason; the changed file itself is listed too, as for other languages, and a file that reads a different object in the same changed file is not impacted. A routine call counts as a read of the routine, so a changed `CREATE FUNCTION` reaches the files that call it. A changed `.sql` file whose statements cannot be mapped still falls back to `fileLevelChange`. Call compatibility stays out of scope because SQL has no callables.
- Application-code strings are not globally linked to SQL objects. The review-context bridge examines only SQL-shaped string or template literal content, so source comments and ordinary identifiers do not surface SQL facts.
- A nested procedural `CASE` containing an `IF` inside a `BEGIN` inside a `CASE` truncates the routine range; references are still found.
- A MySQL routine body without `BEGIN` (a bare `IF`, `LOOP`, `REPEAT`, `WHILE`, or `CASE`) is matched by nesting depth only: a scalar `IF(...)` or `REPEAT(...)` call inside it can extend the routine past its end, and a long body of this kind scans slowly. Tree-first SQL extraction (#408) replaces this tracker.

### Terraform

- Indexing: every `.tf` file in one directory shares one module namespace. Symbols are top-level blocks named by their quoted label: `variable` blocks and `locals` attributes (`variable` kind), `output`, `module`, `resource`, and `data`. Inputs and outputs are the module's exports. `.terraform/` install directories are not discovered.
- Module sources: a `source` that starts with `./` or `../`, or an absolute path inside the project root, depends on every `.tf` file in that directory, including symlinks to files inside the root. Registry, Git, HTTP, and other remote sources stay external, and `codegraph unresolved` lists them.
- Navigation: `goToDefinition`, `findReferences`, rename preview, and impact share one resolver in `src/terraform/`. It resolves `var.`, `local.`, `module.`, `data.<type>.`, and `<type>.<name>` references within the module directory; `module.<name>.<output>` to a called local module's output (with one instance index on `count` and `for_each` calls, or a splat on single and `count` calls); and module call arguments to the called module's inputs.
- Rename preview: a same-kind name in any file of the module is a `name_collision`, and each declaration kind is its own namespace. An input variable cannot take a module meta-argument name such as `source` (`invalid_identifier`). A name that a `check` block uses for its own data source is a `shadowing` conflict.
- Impact treats a module directory as one unit: a change reaches the module's other files and every file of each calling module.
- Partial coverage: references report `partial` when a use cannot be proven: a name declared more than once (it resolves to nothing), an unreadable file, a whole-module value (`value = module.net`, but not `depends_on`), indexes that do not fit the call's `count`/`for_each` instancing, and module resource addresses in `import`, `moved`, and `removed`.
- Not references: `for`, template `for`, and `dynamic` iterators; `count`, `each`, `self`, `path`, and `terraform` values; a `check` block's own data sources.
- Not supported: unquoted block labels, provider configurations and `provider = aws.west` aliases, `ephemeral` resources, `terraform_remote_state` and remote module outputs, and `.tf.json`, `.tfvars`, `.tftest.hcl`, and OpenTofu `.tofu` files. Call compatibility does not apply: Terraform has no user-defined callables.

### Identifiers and file extensions

- Import and alias binding extraction accepts each source language's real identifier grammar rather than an ASCII-narrowed approximation. JavaScript, TypeScript, and TSX use `ID_Start`/`ID_Continue` plus `$`, `_`, and ZWNJ/ZWJ continuations. Python and Rust use `XID_Start`/`XID_Continue`. Go and Kotlin use Unicode letters plus `_` and decimal digits, so they reject the letter-number and combining-mark characters that XID admits. Java follows `Character.isJavaIdentifierStart`/`isJavaIdentifierPart`, C# follows the ECMA-334 identifier grammar including the `@` verbatim prefix, and PHP accepts any byte `>= 0x80` at any identifier position.
- Identifier equality follows each language's own rule, and only where the language defines one. Python compares after NFKC (PEP 3131), Rust after NFC, Java after deleting `Character.isIdentifierIgnorable` characters (JLS 3.8), and C# after removing a leading `@` and formatting characters (ECMA-334). Sass treats `-` and `_` as the same character in SCSS variable, mixin, and function names; namespaces and placeholder names compare as written. Kotlin, Go, and JavaScript/TypeScript compare code points directly, so two differently spelled forms stay distinct symbols. PHP compares class, interface, trait, enum, function, and method names ASCII-case-insensitively; PHP variables, properties, enum cases, class constants, and global constants remain case-sensitive. Canonicalization applies to lookups and comparisons only: stored names, ranges, portable handles, symbol ids, and rename edit text keep the exact source spelling.
- File extension mappings include `.pyw` (Python), `.rbw`/`.rake`/`.gemspec` (Ruby), `.ktm` (Kotlin), `.csx` (C#), `.phtml`/`.php4`/`.php8` (PHP), `.xhtml` (HTML), and `.ddl`/`.pgsql`/`.mysql` (SQL). `.sass` is not mapped: indented Sass produces an ERROR node for every rule under `arborium-scss`. Objective-C (`.m`/`.mm`), Stylus (`.styl`), Go templates (`.templ`), and Zig manifests (`.zon`) are unsupported because no grammar is pinned.
- Default project discovery includes every registered language extension; no custom glob is needed for the aliases above.

Default discovery ignores:

- Always skipped: `node_modules/`, `.git/`, `.codegraph/` (including the disk cache), legacy `.codegraph-cache/`, `dist/`, `build/` (Gradle and similar), and `target/` (Maven and Rust).
- Python: `.venv/`, `venv/`, `site-packages/`, and `__pycache__/`. Bare `env/` is not ignored by default because many repos use that name for configuration, not a virtualenv.
- Ruby: `vendor/bundle/` (Bundler). Bare `vendor/` is left alone so Go and Composer trees that projects intentionally track remain indexable; exclude them with `discovery.ignoreGlobs` when desired.
- Swift and CocoaPods: `.build/` and `Pods/`.
- .NET `bin/` and `obj/` are left alone because `bin/` commonly holds first-party scripts; add those globs explicitly when indexing build output is undesirable.
- Explicit `discovery.includeGlobs` (or CLI `--include-glob`) can re-include a default-ignored directory; user ignore globs and `.gitignore` still win for exclusions.

Monorepo and diagnostic behavior:

- Project file traversal stops at the nearest manifest boundary, so scoped scans do not inherit unrelated parent projects.
- `inspect` and `unresolved` use supported dependency manifests to suppress declared third-party packages from unresolved-import diagnostics.
- Graph-only document and template link edges still appear in graph output. They are excluded from unresolved-import diagnostics by default, so source import health is not mixed with documentation link checking.
- The `links` command and `checkMarkdownLinks()` validate only links authored in Markdown sources: local file and directory targets plus GitHub-style heading fragments, confined to the project root, with external URLs skipped and no network access. Images, MDX, other document formats, and custom HTML or site-generator anchors are not validated.
- Markdown graph extraction and `codegraph links` ignore HTML comments, leading YAML or TOML front matter, images, and indented code, including code after thematic breaks or inside blockquotes. Blockquote prose, nested lists, and list continuation links retain their source coordinates, including CRLF files. List indentation is local to each blockquote.
- AsciiDoc graph extraction skips complete `ifdef`, `ifndef`, and `ifeval` regions without evaluating attributes. Unterminated regions remain visible to extraction.

## C/C++ resolution hints

Configure repo-local include roots with `graph.resolutionHints` in `codegraph.config.json` or CLI `--resolution-hint`. Hints are root-confined, participate in cache identity, and improve candidate-test linkage for layouts such as Unreal-style `Private/.../Tests` includes.

A quoted `#include` resolves against the including file's own directory first, matching the language rule, so `#include "lib.h"` and `#include "inc/lib.h"` bind to first-party siblings without configuration. Angle includes (`#include <lib.h>`) stay external and reach first-party files only through `graph.resolutionHints`. Both C and C++ use this order for dependency edges, navigation, and references.
